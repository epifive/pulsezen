Pulsezen

Privacy-friendly website analytics as a service, built with Next.js 16, React 19 and Tailwind CSS 4. A simple, cookieless alternative to Google Analytics that you run and sell yourself. Open source under the MIT licence. This guide takes you from a fresh clone to a live platform with paying customers.

Quick start: clone the repository and upload its app folder (renamed to pulsezen), run npm install and npm run build, start the app, then open your domain in a browser. The web installer does the rest. Then read Background jobs & scheduling (daily summaries, data retention, alerts and reports depend on it) and Adding the tracking script.

Introduction

Pulsezen lets you run your own website analytics service, like Plausible, Fathom or Simple Analytics. Your customers sign up, add their websites and paste one line of code. The tiny tracking script pz.js (about 1.5 KB gzipped) records pageviews and events without cookies, without local storage and without fingerprinting.

Every website gets a clean, live dashboard: visitors, visits, pageviews, views per visit, bounce rate and visit duration; top pages, entry and exit pages; sources and channels, including traffic from AI assistants such as ChatGPT, Perplexity, Gemini, Copilot and Claude; UTM campaigns; countries, regions and cities; browsers, operating systems, devices, screen sizes and languages; goals, custom events and revenue. Customers get weekly or monthly email reports, traffic alerts (spike, drop, “no data”) by email, Slack, Discord, Microsoft Teams, Telegram or a signed webhook, shared dashboards they can send to clients or embed in an iframe, and a Stats REST API.

You earn money with paid plans. Plans limit the number of websites and monthly pageviews, set how long detailed data is kept, give access to the Stats API and remove the “Powered by” line. Payments are accepted through Stripe (automatic renewal), PayPal, Razorpay or manual bank transfer.

Words used in this guide: you or the administrator run the platform. Customers are the people who sign up on your platform and add websites. Visitors are the people who visit your customers' websites and are counted by Pulsezen. In the examples, your platform lives at https://analytics.example.com and a customer's website at https://example.com.

Installation

Pick the guide that matches your hosting. Every method ends with the web installer, and every method needs a way to run background jobs: read Background jobs right after installing.

Install Pulsezen on its own domain or subdomain, for example https://analytics.example.com or https://stats.yourbrand.com. The tracking snippet contains this address, so changing it later means every customer must update the snippet on every website. Pick a neutral name: some ad blockers block subdomains named analytics. or stats., and some block third-party analytics in general (customers can fix this with a first-party proxy).

cPanel / shared hosting (Setup Node.js App)

  1. In cPanel open MySQL® Databases. Create a database and a user, then add the user to the database with All privileges. Write down the database name, username and password.
  2. Create the subdomain (e.g. analytics.example.com) in Domains and turn on SSL/TLS Status → Run AutoSSL so it has HTTPS.
  3. Open File Manager and upload pulsezen.zip (the repository's app folder renamed to pulsezen, zipped) to your home folder, e.g. /home/youruser/pulsezen, and extract it. Do not put it inside public_html.
  4. Open Setup Node.js App → Create Application:
    • Node.js version: the newest available (22.x recommended)
    • Application mode: Production
    • Application root: pulsezen
    • Application URL: your domain or subdomain
    • Application startup file: server.js
    Click Create.
  5. Click Run NPM Install and wait until it finishes.
  6. Copy the command shown at the top of the page (it looks like source /home/youruser/nodevenv/pulsezen/22/bin/activate && cd /home/youruser/pulsezen). Open Terminal in cPanel, paste it, then run: 
    npm run build
    The build takes 1–4 minutes. It first prints [tracker] public/pz.js … B gzip (the tracking script), then builds the app.
  7. Back in Setup Node.js App, click Restart. Open your domain: you will see the installer.
  8. After installing, add the cron job from Admin → System (see Cron URL). On cPanel this is strongly recommended: Passenger stops idle apps, and lazy mode only runs while there is activity (platform pages or tracked events).

server.js starts the built Next.js app, which serves everything: pages, the API, the event endpoint and the files in public, including /pz.js. You don't need to copy anything into public_html.

If the build stops with “JavaScript heap out of memory” your plan limits memory. Build on your own computer instead (npm install && npm run build), then upload the whole folder including the .next folder and public/pz.js, and only run “Run NPM Install” + “Restart” on the server. Shared hosting is fine for small platforms; event collection on busy websites needs a VPS (see Performance).

VPS (Ubuntu) with PM2 and Nginx

  1. Install Node.js 22, Nginx and PM2: 
    curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs nginx
sudo npm install -g pm2
  2. Install MySQL (or use SQLite and skip this step): 
    sudo apt install -y mysql-server
sudo mysql -e "CREATE DATABASE pulsezen CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'pulsezen'@'localhost' IDENTIFIED BY 'choose-a-strong-password';
GRANT ALL PRIVILEGES ON pulsezen.* TO 'pulsezen'@'localhost'; FLUSH PRIVILEGES;"
  3. Upload the pulsezen folder to /var/www/pulsezen, then build: 
    cd /var/www/pulsezen
npm ci
npm run build
  4. Choose a cron secret and start the app and the worker with PM2. ecosystem.config.cjs starts two processes: pulsezen (the web app) and pulsezen-worker (runs the background jobs every 15 seconds). Both get the same CRON_SECRET: 
    export CRON_SECRET="$(openssl rand -hex 24)"
echo "$CRON_SECRET"          # keep a copy
pm2 start ecosystem.config.cjs
pm2 save && pm2 startup

    Always set your own CRON_SECRET before pm2 start. Without it the worker can't run jobs (PM2 prints a warning and the worker exits), and a CRON_SECRET line in .env.local is only seen by the worker, not by the app. Export the variable before pm2 start (as above) or write your secret into ecosystem.config.cjs. Use at least 12 random characters: the app ignores shorter values and the example value change-me-to-a-long-random-string. After changing it run pm2 restart ecosystem.config.cjs --update-env.

  5. Create /etc/nginx/sites-available/pulsezen: 
    server {
    listen 80;
    server_name analytics.example.com;
    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
    X-Forwarded-For is important: Pulsezen needs the visitor's IP address (only in memory) to tell visitors apart and to find their location. Enable the site and add a free SSL certificate: 
    sudo ln -s /etc/nginx/sites-available/pulsezen /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d analytics.example.com
  6. Open https://analytics.example.com to run the installer. Afterwards, Admin → System → Scheduler should show Running with the source worker within a minute.
Keep instances: 1 for the web app in ecosystem.config.cjs. Events are buffered in memory and written in batches, and rate limits, visit tracking and some caches are kept per process. One Node.js process handles a lot of events (see Performance). The worker calls http://localhost:3000 by default; set WORKER_URL if the app listens elsewhere.

Docker

The app folder includes a Dockerfile and a docker-compose.yml with three services: app (the web app), worker (runs background jobs every 15 seconds) and db (MySQL 8.4). First create a file named .env next to docker-compose.yml with your own secret:

CRON_SECRET=paste-a-long-random-string-here

Then start everything:

cd pulsezen
docker compose up -d --build

Open http://your-server:3000. In the installer choose MySQL with host db, port 3306, database pulsezen, user pulsezen, password pulsezen (change these and MYSQL_ROOT_PASSWORD in docker-compose.yml first). The storage folder is kept in a Docker volume. Put Nginx, Caddy or Traefik with HTTPS in front of port 3000, and make sure it sends X-Forwarded-For.

docker-compose.yml refuses to start until CRON_SECRET is set in the .env file next to it (at least 12 random characters). The included .dockerignore keeps local node_modules, .next and storage folders out of the image. For a GeoIP file, copy it into the storage volume (e.g. /app/storage/GeoLite2-City.mmdb) and enter that path in Admin → Settings → Analytics.

Without Compose:

docker build -t pulsezen .
docker network create pulsezen-net
docker run -d --name pulsezen --network pulsezen-net -p 3000:3000 \
  -e CRON_SECRET=your-secret -v pulsezen-storage:/app/storage pulsezen
docker run -d --name pulsezen-worker --network pulsezen-net \
  -e WORKER_URL=http://pulsezen:3000 -e CRON_SECRET=your-secret pulsezen node scripts/worker.mjs

Vercel (with a cloud MySQL database)

Vercel has no permanent disk, so the web installer and SQLite can't be used there. Instead, Pulsezen is configured with environment variables and a cloud MySQL-compatible database such as TiDB Cloud Serverless (free tier), Aiven or PlanetScale. A nice bonus: Vercel sends the visitor's country, region and city with every request, so locations work without a GeoIP file.

  1. Create a database. In TiDB Cloud: create a Serverless cluster in the region closest to your Vercel functions, open Connect, generate a password and note the host, port (4000), user and password. In the SQL editor run CREATE DATABASE pulsezen;
  2. Fork this repository on GitHub (or push your own copy).
  3. In Vercel click Add New → Project, import the repository and set Root Directory to app (the folder that contains package.json). Keep the default build command (npm run build): it also builds pz.js.
  4. Add these Environment Variables: 
    DB_DRIVER=mysql
DB_HOST=gateway01.ap-southeast-1.prod.aws.tidbcloud.com
DB_PORT=4000
DB_USER=xxxxxxxx.root
DB_PASSWORD=your-password
DB_NAME=pulsezen
DB_SSL=true
APP_INSTALLED=true
ADMIN_EMAIL=you@example.com
ADMIN_PASSWORD=a-strong-password
ADMIN_NAME=Your Name
SITE_URL=https://analytics.example.com
CRON_SECRET=a-long-random-string
  5. Click Deploy. Tables are created automatically on the first visit and the administrator account is created from ADMIN_EMAIL / ADMIN_PASSWORD.
  6. Add your domain in Settings → Domains, and set the same address in Admin → Settings → General → Site URL.
  7. In Vercel open Settings → Functions and choose the region closest to your database.
  8. Set up the scheduler as described in Vercel & serverless. This step is not optional on Vercel.

Vercel is fine for a demo or a small platform, but a VPS is cheaper and faster for an analytics service:

  • Every event is one function call and one database write. On busy websites this uses a lot of function invocations and database request units.
  • On Vercel each event is written right after its request (no batching across requests), and rate limits and visit caches are kept per serverless instance.
  • There is no worker process, so background jobs depend on an external cron service.
  • Uploaded files are not kept (no permanent disk). Paste image URLs for your logo and favicon instead of uploading.

Local computer (for testing or customising)

cd pulsezen
npm install
npm run dev

Open http://localhost:3000 and choose SQLite in the installer. Lazy mode is on by default, so background jobs run while you click around. To run them without visiting pages, start the worker in a second terminal (copy the secret from Admin → System → Scheduler):

CRON_SECRET=the-secret-from-admin npm run worker

On Windows PowerShell: $env:CRON_SECRET="the-secret"; npm run worker.

To test tracking on your computer, add a website with the domain localhost (or switch on Count visits from localhost in its settings) and add data-allow-localhost to the snippet. Without both, the script ignores localhost pages on purpose. See Troubleshooting.

Web installer

  1. Requirements – checks the Node.js version and that storage is writable.
  2. Database – choose MySQL/MariaDB (host, port, database, user, password, and Use SSL for cloud databases) or SQLite. Click Test connection, then Continue.
  3. Site & admin – enter your platform name, the full site URL (e.g. https://analytics.example.com) and the administrator account. Click Install now.

First steps after installing

The admin dashboard shows a Finish setting up checklist. In short:

  1. Settings → General: check the Site URL. It must be your public https:// address: the tracking snippet, dashboard links in alerts, email reports and the cron URL are built from it. Add your logo and contact email.
  2. Admin → System → Scheduler: set up the cron URL or the worker (see Background jobs) and check that the badge says Running.

Adding the tracking script

This chapter is for you and your customers: you can copy parts of it into your own help pages. Each website's Install page in the dashboard (/dashboard/sites/<id>/install) also shows the snippet, short guides for common platforms and a live check that waits for the first visit.

The snippet

Paste this into the <head> of every page. The dashboard shows it with the right address and site key (a 12-character code, also shown in Site settings):

<script defer src="https://analytics.example.com/pz.js" data-site="YOUR_SITE_KEY"></script>

That's all. Within seconds of the first visit, the Install page says It works! and the site settings show Receiving data since …. The script:

  • sends one small request per pageview or event (navigator.sendBeacon, or fetch with keepalive and no credentials);
  • sets no cookies and uses no localStorage or sessionStorage;
  • does nothing for automated browsers (navigator.webdriver, Cypress, PhantomJS, Nightmare), for file: pages and, unless allowed, for localhost;
  • waits until a prerendered page is actually shown;
  • catches all its own errors, so it can never break the website.

Known bots, crawlers, link previews and browser prefetches are also filtered out on the server.

Script options

All options are data-* attributes on the script tag.

AttributeDefaultWhat it does
data-site(required)The site key.
data-api<script origin>/api/eventWhere events are sent. Needed with a first-party proxy.
data-excludenoneComma-separated path patterns that are not tracked; * matches anything: data-exclude="/admin/*, /preview/*". Matched against the page path in the browser. (Customers can also exclude paths on the server in Site settings → Pages to ignore.)
data-hashoffHash-based routing: #/page changes are tracked as pageviews, stored as /#/page. See below.
data-outboundonSends an Outbound Link event when a link to another website is clicked. data-outbound="false" turns it off.
data-downloadsonSends a File Download event for links to files: pdf, zip, rar, 7z, gz, tgz, doc(x), xls(x), ppt(x), csv, txt, rtf, odt, ods, epub, mp3, wav, mp4, mov, avi, mkv, dmg, pkg, exe, msi, apk, iso, deb, rpm. data-downloads="false" turns it off; data-downloads="pdf,zip" tracks only those extensions.
data-404offPut it on the snippet of your “page not found” template: the page sends a 404 event instead of a pageview.
data-respect-dntoffDon't track visitors whose browser sends “Do Not Track”.

Example with several options:

<script defer src="https://analytics.example.com/pz.js" data-site="YOUR_SITE_KEY"
  data-exclude="/admin/*, /checkout/*" data-downloads="pdf,zip" data-respect-dnt></script>

Single-page apps and hash routing

Single-page apps (React, Vue, Next.js, Nuxt, SvelteKit, Angular …) need nothing extra. The script follows history.pushState, history.replaceState and the back/forward buttons and sends a pageview whenever the path changes. Changes of the query string alone (e.g. ?tab=2) don't create a new pageview, and the same path is never counted twice in a row.

Apps whose pages look like https://example.com/#/settings use hash routing. Add data-hash to the snippet. Hash routes that start with #/ or #!/ are then stored as pages such as /#/settings. For other hash styles (e.g. #settings) also switch on Hash routing in the site settings. Without data-hash the part after # is never sent.

Query strings are never stored as part of the page. /pricing?ref=x is stored as /pricing. Only the campaign parameters (utm_source, utm_medium, utm_campaign, utm_term, utm_content, and ref / source as a fallback for utm_source) and ad click ids (to detect the Paid channel) are read. Trailing slashes are removed (/blog/ = /blog).

Outbound links, file downloads and 404 pages

  • Outbound Link (on by default): a click (or middle-click) on a link whose host differs from the page's host. www.example.com and example.com are different hosts here, so links between them count as outbound.
  • File Download (on by default): a click on a link to one of the file types above. The address of the link is saved as the url property.
  • 404 (opt-in with data-404): the not-found page counts as a 404 event instead of a pageview, so broken links show up in the Custom events tab and can become a goal.

These events count towards the monthly pageview limit like any custom event. They appear in the Custom events tab of the Goals and events card and can be used as goals.

The clicked URL is saved with each Outbound Link and File Download event as the property url. Click the event in the Custom events tab to see which links were clicked and which files were downloaded (see Event properties).

Custom events, properties and revenue

Once the snippet is installed, the page has a global function pulsezen():

pulsezen("Signup");
pulsezen("Signup", { props: { plan: "Pro", source: "pricing-page" } });
pulsezen("Purchase", { props: { plan: "Pro" }, revenue: { amount: 49.99, currency: "USD" } });
pulsezen("Download", { callback: () => (location.href = "/thanks") });
PartRules
Event nameUp to 120 characters; < and > are removed. Names are case-sensitive everywhere (goals, filters, MySQL and SQLite alike): Signup and signup are different events. Don't use the name pageview: it is reserved for pageviews.
propsUp to 20 properties. Keys up to 40 characters, values (string, number or boolean) up to 200 characters. Keys starting with $ are reserved. Properties are saved with the event and shown when you click the event in the dashboard (Event properties).
revenueamount in major units (49.99) and an optional ISO 4217 currency code (3 letters). Stored in cents. The currency is kept as the reserved property $currency. Revenue on pageviews is ignored.
callbackCalled once the event has been handed to the browser (also when the event is skipped, e.g. on localhost), so it is safe for redirects.
Revenue is counted in the platform currency only (Admin → Settings → Payments → Currency). Amounts sent in that currency, or without a currency, are added up as revenue. Amounts in any other currency are not added (there is no currency conversion): the event and its $currency property are still saved, so the event's property breakdown shows how many such events arrived. Websites should send revenue in the platform currency.

To send events before pz.js has loaded (e.g. from an inline script near the top of the page), add this one-liner before the snippet. Queued calls are sent right after the first pageview:

<script>window.pulsezen=window.pulsezen||function(){(window.pulsezen.q=window.pulsezen.q||[]).push(arguments)}</script>

In TypeScript / React, call it safely like this:

declare global { interface Window { pulsezen?: (name: string, options?: object) => void } }

window.pulsezen?.("Signup", { props: { plan: "Pro" } });

Then add a goal with the same event name to see conversion rates.

Events without JavaScript: CSS classes

Add pulsezen-event-name=EVENT_NAME to the class list of a link, button or form (use + for spaces). Extra pulsezen-event-KEY=VALUE classes become properties:

<a href="/signup" class="button pulsezen-event-name=Signup+Click pulsezen-event-plan=pro">Start free</a>
<form action="/contact" method="post" class="pulsezen-event-name=Contact+Form">…</form>

On links, buttons and other elements the event is sent when the element (or something inside it, up to 6 levels deep) is clicked. On a <form> the event is sent when the form is submitted (after the browser's own validation passed), not on clicks inside it. This works in page builders that let you add CSS classes (WordPress block editor, Elementor, Webflow, Wix …).

The event endpoint

The script sends one POST per event to /api/event, with a text/plain JSON body of at most 2 KB:

{ "n": "pageview", "u": "https://example.com/pricing?utm_source=x", "d": "SITE_KEY", "r": "https://www.google.com/", "w": 1440 }

n event name, u page URL (the hash only with data-hash), d site key, r referrer, w viewport width, and optionally p properties and $ revenue. You can also send events from a server or an app with the same format (Content-Type: text/plain or application/json); send a real browser User-Agent and the visitor's IP in X-Forwarded-For, or the event is treated as a bot or as the server's own visit.

AnswerMeaning
202 (no body)Accepted — or silently ignored: bots, excluded paths or IP addresses, over the plan limit, or the website owner's account is banned. Ignored events never reveal themselves, so bots can't probe the filters.
400Invalid payload (missing name, invalid site key or URL …).
403The page's hostname is not the website's domain, one of its subdomains or one of the site's Other domains.

Errors have a JSON body like {"error":"Unknown site."}. The endpoint allows any origin (Access-Control-Allow-Origin: *, no credentials); the page's hostname is checked against the website's domains instead. Like with any client-side analytics, the site key is public. This is true of every web analytics tool; rate limits and the bot filter keep it bounded, and customers can reset a website's statistics if it ever happens.

First-party proxy (against ad blockers)

Some ad blockers and privacy extensions block requests to third-party analytics domains, or common analytics paths. Typically 5–25 % of visitors use one, more on technical websites. Customers can avoid this by serving the script and the endpoint from their own domain through a small proxy. Point src and data-api at the proxy:

<script defer src="/stats/js/script.js" data-api="/stats/api/event" data-site="YOUR_SITE_KEY"></script>

The proxy must forward the visitor's IP address in X-Forwarded-For (all examples below do). Pulsezen uses the first address of that header for the anonymous visitor id, the location and IP exclusions. Without it, every visitor would look like the proxy server and be counted as one person.

Replace analytics.example.com with your platform's domain. Use neutral paths (not /analytics/ or /pulsezen/).

Checking the proxy

  • Open https://example.com/stats/js/script.js: you should see the minified script.
  • Visit the website with an ad blocker on; the visit should appear in the dashboard within seconds (realtime counter).
  • If all visits come from one city or count as one visitor, X-Forwarded-For is missing.

Rate limits: a proxy sends the events of all its visitors from one IP address. An event counts as proxied when the visitor address in X-Forwarded-For differs from the address that connected to your platform. Proxied events are limited per visitor (120 per minute) and per proxy address and website (600 per minute by default, setting EVENT_PROXY_RATE_LIMIT_PER_MIN). The proxy limit is kept moderate because anyone can put made-up addresses into X-Forwarded-For to look like many visitors; raise it when a busy website sends more than about 10 events per second through its proxy.

Locations: Vercel and Cloudflare location headers describe the connection to your platform, which for proxied events is the proxy server. Pulsezen therefore ignores them for proxied events and looks up the forwarded visitor IP in the GeoIP file instead. Without a GeoIP file, proxied events have no location (country “unknown”). Direct (not proxied) events keep using the headers.

How visitors are counted

Pulsezen counts visitors without cookies. This chapter explains exactly how, so you can answer your customers' questions (“why is this different from Google Analytics?”).

The anonymous visitor id

For every event the server computes:

visitor id = SHA-256( daily salt + visitor IP + User-Agent + website id ), first 32 hex characters
  • The daily salt is a random 32-byte value created for every UTC day and stored in the database. When the first event of a new day creates that day's salt, salts older than yesterday are deleted (the retention job deletes them as well), so this works even without background jobs. Once a salt is gone, nobody — not even you — can link an id back to an IP address or to the same person on another day.
  • The IP address is used only in memory, for this hash, the location lookup, IP exclusions and rate limits. It is never stored.
  • Because the website id is part of the hash, the same person gets unrelated ids on different websites.

Metric definitions

MetricDefinition
VisitorsDistinct visitor ids in the period. The id changes every day, so over several days this is the sum of daily unique visitors: a person who comes back on three days counts three times (the same way Plausible counts).
VisitsA visit starts with the first event of a visitor and ends after 30 minutes without any event. The next event starts a new visit.
PageviewsEvents named pageview.
EventsEvery other event (custom events, Outbound Link, File Download, 404).
Views per visitPageviews ÷ visits.
Bounce rateVisits made of exactly one pageview and nothing else, ÷ visits. A visit with one pageview and a custom event (or an outbound click) is not a bounce.
Visit durationAverage over visits of the time between the visit's first and last event. A visit with a single pageview has a duration of 0 (there is no “ping” while the page stays open).
Entry / exit pageThe page of a visit's first event / its last pageview.
Realtime visitorsDistinct visitor ids with an event in the last 5 minutes. The dashboard refreshes it every 15 seconds.
Conversion rateVisitors who completed the goal ÷ visitors.

Visit-level information (source, channel, UTM, location, browser, device, entry page) comes from the visit's first event. Filters on these dimensions select whole visits; filters on page, hostname, event and goal select single events.

Sources and channels

The source is the referrer's website, normalised to a name (“Google”, “ChatGPT”, “Reddit”, or the hostname for unknown sites). A utm_source (or ref / source) parameter overrides the referrer. Links from the website to itself are not referrers. The channel is decided in this order:

  1. Paid – utm_medium such as cpc, ppc, paid, display, or an ad click id (gclid, gbraid, wbraid, msclkid, dclid, ttclid, twclid, li_fat_id, gad_source).
  2. Email – utm_medium email/newsletter, a utm_source containing newsletter or email, or webmail (Gmail, Outlook, Yahoo Mail, Proton Mail).
  3. Social – utm_medium=social or a known network (X, Facebook, Instagram, LinkedIn, Reddit, YouTube, TikTok, Pinterest, Threads, Bluesky, Mastodon, Hacker News, WhatsApp, Telegram, Discord …).
  4. AI assistants – ChatGPT, Perplexity, Gemini, Copilot, Claude, DeepSeek, Poe, You.com, Phind, Meta AI, Grok, Mistral, Kimi.
  5. Search – Google, Bing, DuckDuckGo, Yahoo, Yandex, Baidu, Ecosia, Brave Search, Startpage, Qwant, Kagi, Naver, Seznam, or utm_medium=organic.
  6. Referral – any other referrer or utm_source.
  7. Direct – no referrer and no campaign parameters (typed URL, bookmark, many apps). Shown as the source Direct / None.

AI assistants often send no referrer at all (especially their mobile apps); such visits count as Direct. Many AI tools add utm_source=chatgpt.com to links, which Pulsezen recognises.

Accuracy: what to expect

  • Ad blockers may block the script or the endpoint. A first-party proxy recovers most of these visits.
  • Visitors without JavaScript and most bots are not counted (on purpose).
  • Returning visitors are new visitors every day: there is no long-term visitor id, so “new vs returning” isn't available.
  • People behind the same IP address with the same browser version (an office, a school, some mobile networks) share one id on that day. A phone that changes networks during a day (Wi-Fi to mobile data) gets a new id.
  • The salt changes at midnight UTC. A visit that continues past midnight UTC starts again as a new visitor and visit. For websites in a time zone far from UTC, the “unique visitors” of one local day can therefore count a few people twice.
  • Visit duration is shorter than Google Analytics' engagement time, because the time on the last page of a visit is not known.
Why numbers differ from Google Analytics: GA4 uses cookies (a returning visitor is the same user for up to two years), is blocked more often by ad blockers and consent banners (visitors who decline aren't counted, or are modelled), filters bots differently and defines sessions, bounce and engagement differently. Differences of 10–40 % are normal. Compare trends, not exact numbers.

Background jobs & scheduling

Events are collected the moment they arrive; that never depends on the scheduler. But several important things happen in the background, and something must start them. Read this chapter before you invite customers.

How it works

A tick runs these jobs one after the other, within a time budget. Each job does a small slice of work and remembers when it should run again, so ticks every 15 seconds are cheap. Whatever doesn't fit is picked up by the next tick. A lock in the database makes sure two ticks never run at the same time.

JobWhat it doesHow often
rollupsBuilds the daily summaries of finished days, in each website's time zone, about 3 minutes after local midnight. Up to 40 days per tick (a backlog is spread over several ticks).Looks every 5 minutes
retentionDeletes raw events older than the owner's plan allows (only days that are already summarised; at most 5,000 events per website per tick), visitor salts older than yesterday, and alert log entries older than 90 days.Every hour (sooner while there is a backlog)
traffic-alertsChecks every active traffic alert and sends the alerts.Every 5 minutes
reportsSends due weekly (Monday) and monthly (1st) email reports, up to 20 per tick. Waits while SMTP isn't configured.Every 10 minutes
usageEmails customers who reach 80 % and 100 % of their monthly pageview limit (once each per month, up to 50 per tick). Waits while SMTP isn't configured.Every 15 minutes

Long date ranges are also slower without summaries. (Old visitor salts are deleted even without ticks: when the first event of a new day creates that day's salt.)

The cron secret

The cron URL and the worker are protected by a secret:

  • If the environment variable CRON_SECRET is set (at least 12 characters, not the example value), that value is the secret.
  • Otherwise Pulsezen creates a random secret the first time it is needed and stores it in the database.

To see it, open Admin → System. The Scheduler card shows the complete Cron URL (with a Copy button) and a ready-made cron line. Click New secret to replace a stored secret, e.g. if it leaked; the old URL stops working immediately, so update your cron job and worker. The button is hidden while the secret comes from CRON_SECRET: change the environment variable instead and restart. (A CRON_SECRET that is ignored because it is too short or the example value doesn't count: then the stored secret is in use and the button works.)

The secret can be sent in two ways:

curl -fsS "https://analytics.example.com/api/cron/tick?key=YOUR-SECRET"
curl -fsS -H "Authorization: Bearer YOUR-SECRET" https://analytics.example.com/api/cron/tick

GET and POST both work. A correct call answers with a JSON summary, for example {"source":"cron","startedAt":"…","jobs":{"rollups":3,"retention":0,"traffic-alerts":0,"reports":1,"usage":0},"failed":[],"skipped":[],"durationMs":840,"skippedLocked":false}. The numbers are the items each job handled (days summarised, events deleted, alerts sent, reports sent, usage emails sent). A wrong or missing secret answers 401. More than 30 calls per minute from one IP address answer 429.

Lazy mode (default, no setup)

With Settings → Analytics → Run background jobs on visits switched on, the platform runs a tick after it has answered a page request or a tracked event (POST /api/event), whenever no tick ran during the last minute. The visitor never waits. A lazy tick has an 8-second time budget, and each server process tries at most once every 15 seconds.

Lazy mode only works while there is activity: people opening your platform's pages (public site, dashboard, admin panel) or events arriving from your customers' websites. At night, or on a new platform, nothing may run (e.g. no report goes out on time and no “no traffic” alert fires). On cPanel, Passenger also stops the app after a period without requests. Use it to get started, then add the cron URL or the worker. You can leave lazy mode on as a backup: it does nothing while cron or the worker keep ticks fresh.

Data retention & rollups

Analytics data grows fast: every pageview is one row. Pulsezen keeps the database small with two kinds of data:

DataWhat it isHow long it is kept
Raw eventsOne row per pageview or event, with page, source, location, device, visit, visitor id and custom properties.The owner's plan's Keep detailed data (days): Free 30, Pro 365, Agency 730 by default. 0 = forever. Websites of administrators are never pruned. Customers without an active paid plan use the free plan's value; if no plan is marked as the free plan, Settings → Analytics → Keep detailed data applies (default 30, like the free plan).
Daily summaries (rollups)One row per website, day (in the website's time zone), dimension and value: visitors, visits, pageviews, events, bounces, total duration and revenue. Raw events are deleted only after their day has been summarised, so nothing is lost by mistake. The dashboard reads old days from the summaries automatically: a customer on the Free plan still sees a full 12-month chart, top pages, sources and countries for every month. Unfiltered ranges of three months or more also read finished days from the summaries, which makes long ranges fast.

What needs raw events

Summaries can answer “no filter” and a single “is” filter exactly for the totals and the chart (e.g. country is DE, or page is /pricing), and for the list of that same dimension. They can't combine dimensions. For days that only exist as summaries:

  • With two or more filters, or is not / contains filters, those days are left out everywhere, and the dashboard shows a notice: “Some days in this range only have daily summaries … These filters can't be applied to them, so those days are left out.” The Stats API returns "approximate": true.
  • With a single “is” filter, the totals and the chart include those days, but lists by other dimensions (e.g. pages while filtering by country) and goal conversions leave them out. The dashboard shows a notice about this, and Stats API breakdowns return "approximate": true.
  • The AI assistants tab (sources in the AI channel) reads the summaries of the known AI sources, so long ranges are complete.
  • Hourly charts are empty for those days (only today and yesterday use hourly charts, so this matters only with a retention of 1 day).
  • Pageview goals with a wildcard (e.g. /blog/*) count a visitor once per matching page per day, so unique conversions can be slightly higher than with raw data.
  • Realtime visitors and event properties need raw events: properties are not summarised, so the property lists only count days that still have raw events.
Plan retention is applied every hour by the retention job. When a customer downgrades (or a paid plan ends), the free plan's retention applies from then on, and older raw events are deleted at the next run. Upgrading later can't bring them back; the summaries stay. Mention this on your pricing page.
Changing a website's time zone rebuilds the summaries of every day that still has raw events in the new time zone (the rollups job does it within a few minutes). Older days whose raw events were already deleted keep their old day boundaries.

GeoIP: countries, regions and cities

Pulsezen finds a visitor's location in this order, and never stores the IP address:

  1. Vercel headers (x-vercel-ip-country, -country-region, -city) when the platform runs on Vercel.
  2. Cloudflare headers when the platform's domain is proxied by Cloudflare: cf-ipcountry (countries, on by default), plus cf-region and cf-ipcity if you enable Rules → Managed Transforms → Add visitor location headers in Cloudflare.
  3. A GeoIP database file (.mmdb) on your server, configured in Settings → Analytics.

Without any of these, the location columns stay empty (“Unknown”). The database file is not included in the repository, because its licence doesn't allow redistribution. Two free options:

MaxMind GeoLite2 City (free account needed)

  1. Create a free account at maxmind.com/en/geolite2/signup and sign in.
  2. Open Download Databases and download GeoLite2 City (GZIP, the .mmdb format). Unpack it: you get GeoLite2-City.mmdb (about 60 MB). GeoLite2 Country (about 8 MB) works too, without regions and cities.
  3. Upload the file to your server, outside public folders, e.g. /var/www/pulsezen/storage/GeoLite2-City.mmdb.
  4. In Admin → Settings → Analytics enter the full path in GeoIP database file and save.
  5. Restart the app (the file is loaded once and kept in memory).

Licence: GeoLite2 is free under the GeoLite2 End User License Agreement. You must keep it up to date (MaxMind asks you to use the latest release and delete old copies within 30 days) and show the attribution “This product includes GeoLite2 data created by MaxMind, available from https://www.maxmind.com” — for example in your Privacy policy or footer. Read the EULA for commercial use. For automatic updates, use MaxMind's geoipupdate tool with your licence key (e.g. a weekly cron job), then restart the app.

DB-IP IP to City Lite (no account)

  1. Open db-ip.com/db/download/ip-to-city-lite and download the MMDB version (dbip-city-lite-YYYY-MM.mmdb.gz). Unpack it. (IP to Country Lite works too.)
  2. Upload it to the server and enter its full path in Settings → Analytics, e.g. /var/www/pulsezen/storage/dbip-city-lite.mmdb. Restart the app.
  3. DB-IP publishes a new file every month; replace the file (keep the same name) and restart.

Licence: Creative Commons Attribution 4.0. You must credit DB-IP, e.g. “IP Geolocation by DB-IP” on a page your visitors can see (Privacy policy or footer).

The path must end in .mmdb. A missing or broken file is logged once ([pulsezen] GeoIP database not loaded …), retried every 10 minutes, and never stops event collection. Locations are only added to new events; past events are not looked up again. On Docker, put the file into the storage volume. On Vercel, the headers already provide locations.

Verifying the signature

X-Pulsezen-Signature is only sent when the channel has a signing secret. It is sha256= followed by the hex HMAC-SHA256 of the raw request body, keyed with the secret. Always compute it over the raw bytes, before parsing the JSON, and compare in constant time.

Node.js (Express):

import crypto from "node:crypto";
import express from "express";

const SECRET = process.env.PULSEZEN_SECRET; // the channel's signing secret
const app = express();

app.post("/pulsezen", express.raw({ type: "application/json" }), (req, res) => {
  const expected = "sha256=" + crypto.createHmac("sha256", SECRET).update(req.body).digest("hex");
  const given = req.get("X-Pulsezen-Signature") || "";
  const valid = given.length === expected.length &&
    crypto.timingSafeEqual(Buffer.from(given), Buffer.from(expected));
  if (!valid) return res.status(401).send("Bad signature");

  const alert = JSON.parse(req.body.toString("utf8"));
  console.log(alert.event, alert.site?.domain, alert.message);
  res.sendStatus(204);
});

app.listen(3000);

Privacy

Pulsezen is designed for privacy: no cookies, no persistent identifiers, no IP addresses in the database, and data stays on your own server. That is a strong selling point. But privacy law differs by country and changes over time, so please read this chapter carefully.

Not legal advice. Many data protection authorities treat cookieless, anonymous analytics like this as low-risk, and many websites use it without a consent banner. Some authorities may still consider the short-lived processing of IP addresses (for the daily hash and the location lookup) as processing of personal data. Check the law where you and your customers operate, and ask a lawyer if in doubt. You are responsible for your platform (your own Privacy policy, terms and any data processing agreement with customers); your customers are responsible for informing their own visitors, for example in their privacy policy.

What is stored for each pageview or event

  • Time, website, event name, page path (without the query string; the hash only for hash routes) and hostname.
  • The referrer's hostname and path (without its query string), the derived source and channel, and the UTM parameters.
  • Country, region and city (looked up from the IP address, which is then discarded).
  • Browser name and major version, operating system, device type (desktop, mobile, tablet), a screen-width group and the primary browser language.
  • The anonymous daily visitor id (a hash, see How visitors are counted), a random visit id and the seconds since the visitor's previous event.
  • Custom properties and revenue, if the website sends them.

What is not stored

  • IP addresses (used only in memory for the hash, the location, IP exclusions and rate limits).
  • The full user agent, cookies, device fingerprints, full screen resolution or any id that lasts longer than a day.
  • Query strings, except the UTM / ref / source parameters.

The daily salts are deleted after about two days (when the next day's salt is created, and by the retention job), after which the ids can't be linked to anything. Raw events are deleted after the plan's retention period; daily summaries contain no visitor ids at all.

What your customers must take care of

  • No personal data in URLs, event names or properties. Page paths are stored as they are. A path like /users/jane@example.com, /reset-password/<token> or a property email would be stored too. Exclude such pages (data-exclude or Pages to ignore) and never send names or emails as properties.
  • Mentioning the analytics in their privacy policy, and honouring local rules (e.g. turning on data-respect-dnt where expected).

Your own platform

Your platform itself stores normal account data: names, emails, scrypt password hashes, payments, contact messages (with the sender's IP address), and for signed-in sessions the IP address and user agent. It sets a session cookie for signed-in users, a language cookie and, for unlocked password-protected shared dashboards, a 7-day access cookie. The cookie notice (Settings → Users) is for your own site. Customers can delete a website's statistics (Reset data) or the website itself at any time. Review the default Privacy policy page, add the GeoIP attribution if you use a GeoIP file, and add your company details.

Performance & capacity

How events are written

On a normal server, accepted events are kept in a memory queue and written to the database in multi-row inserts every 2 seconds or every 200 events, together with the monthly usage counters. The visitor's browser gets its 202 answer immediately. If the database is briefly unavailable, the queue keeps up to 50,000 events and retries every 5 seconds. Events still in the queue when the process is killed are lost, so stop the app gracefully (PM2, Docker and systemd do).

On serverless hosts (Vercel, Netlify, AWS Lambda, or PULSEZEN_SERVERLESS=1) every request writes its own events before the function is frozen. This works, but costs one database write per event.

Rough capacity guide

These are estimates for a well-configured server; real numbers depend on the database, disk and how many customers look at their dashboards. “Events” means pageviews plus custom events.

Disk: plan roughly 0.5–1 KB per raw event including indexes (1 million events ≈ 0.5–1 GB). Retention keeps this bounded: a Free customer with 10,000 pageviews a month never holds more than about one month of raw events. Daily summaries are small (one row per website, day, dimension and value).

Indexes: the events table has indexes on (site_id, ts), (site_id, name, ts), (site_id, session_hash, ts) and (site_id, visit_id); rollup_daily has the primary key (site_id, day, dimension, value). They are created by the installer; don't remove them.

Query speed: dashboards of big websites over long ranges are the most expensive part (counting distinct visitors over millions of rows). Unfiltered ranges of three months or more read daily summaries, which keeps them fast; filtered long ranges read raw events. If dashboards get slow, add RAM for MySQL, lower the plans' retention, or move the database to its own server.

One process: keep one app process (instances: 1). The event queue, visit tracking, rate limits and caches are per process. With several processes or servers, numbers stay correct (visits are looked up in the database as a fallback), but rate limits apply per process and the realtime counter may miss events still queued in another process.

Rate limits use the connecting IP address from X-Forwarded-For. Set TRUSTED_PROXY_HOPS correctly when you use Cloudflare in front of Nginx.

Adding a source rule

Add an entry to RULES in src/lib/sources.ts:

{ name: "Le Chat", channel: "ai", host: /^chat\.example-ai\.com$/, aliases: ["lechat"] },

host is matched against the referrer's hostname (lower case, without www.); path is an optional regex for the referrer path; aliases are utm_source values. The first matching rule wins, so put specific rules (e.g. an AI assistant on a search engine's domain) before general ones. Rules apply to new events; old events keep their source.

Adding a dimension

  1. Add a new migration in src/lib/db/migrations.ts (a new key such as "2026_11_01_000001_events_os_version") that adds the column to events, and the column to EventsTable in src/lib/db/schema.ts.
  2. Add the name to DIMENSIONS in src/analytics/types.ts.
  3. Fill the column in the event row in handleEvent() (src/lib/ingest.ts).
  4. Map it to the column in COLUMN in src/lib/query.ts (and add it to EVENT_LEVEL if it describes single events rather than visits).
  5. Add it to VISIT_COLUMNS (or the event dimensions) and the Row type in src/lib/rollups.ts, so old days keep it.
  6. Add a tab in src/components/dashboard/stats-tabs.ts and the texts dash.dim.* / dash.tab.* in messages.ts.

Adding an alert channel

Updating to a new version

  1. Back up the storage folder and your database.
  2. Replace all files except storage (and your .env file and your edited ecosystem.config.cjs, if any) with the new version.
  3. Run npm install and npm run build (this also rebuilds pz.js).
  4. Restart the app and the worker: pm2 restart all, docker compose up -d --build, or Restart in cPanel.

Database changes are applied automatically the first time the new version starts. Websites, statistics, site keys, share links and API keys are kept; customers don't need to change their snippets. During the restart (usually a few seconds) the event endpoint is unavailable and those events are lost; events already queued are written before a graceful stop.

Telegram test fails“Telegram rejected the bot token” = wrong token. “Check the chat ID” = wrong chat ID (groups are negative, supergroups and channels start with -100). “The bot can't write to this chat” = press Start in the bot chat, add the bot to the group, or make it an admin of the channel.
Slack test fails with 403/404The webhook was revoked or the app removed from the channel. Create a new incoming webhook.
Discord test fails401/404: the webhook was deleted; copy a new URL. 400: Discord refuses webhook names containing “discord”; alerts are posted under your site name, so rename your platform if it contains that word.
Teams test failsOld Office 365 connector URLs stop working as Microsoft retires them. Create a Workflow with “Post to a channel when a webhook request is received”.
Webhook: private addresses refusedThe URL points at a local network. Use a public address, or set ALLOW_PRIVATE_WEBHOOKS=1 on a single-company install.
Webhook: “The endpoint answered HTTP 301/302”Redirects are not followed. Use the final https:// address.
Signature doesn't matchCompute the HMAC over the raw body before parsing it, with the channel's current secret, and compare with the whole header including sha256=.
Links in alerts, reports or the snippet point to localhost:3000Set the Site URL in Settings → General.
